## Technical Decisions

| Date | Decision | Rationale | Impact |
|------|----------|-----------|--------|
| 2026-09-19 | LittleFS filesystem for Web Portal assets | Hardcoding HTML/CSS/JS in C++ raw string literals bloats code files and makes frontend iteration cumbersome. Separating them into `data/` with LittleFS enables clean asset management, browser caching, and independent filesystem flashing via `pio run -t uploadfs`. | Created `data/index.html`, `data/css/style.css`, `data/js/app.js`. Configured `board_build.filesystem = littlefs` in `platformio.ini`. `WebPortal` dynamically streams assets with correct MIME types and provides graceful fallback. |
| 2026-09-19 | Multi-point calibration via frontend regression + backend apply | Frontend computes least-squares regression from captured (weight, raw) points; backend only stores pre-computed slope + intercept. This keeps ESP32 firmware minimal while enabling research-grade calibration with R² and standard error metrics. | New `/api/calibrate/multi` endpoint, `CMD_CALIBRATE_MLR` command, `interceptCounts` field in NVS and Modbus map (40030-31). Backward-compatible: single-point calibration via `/api/calibrate` still works. |
| 2026-09-20 | Calibration persistence must be single-writer on one core | `Preferences`/NVS is not safely reentrant across ESP32 cores. Network task and sensor task must not write calibration simultaneously. | Removed duplicate NVS write from `WebPortal::handleApiCalibrateMulti()`. Only `Scale::applyCalibration()` on sensor core persists calibration via `SettingsStore::saveCalibration()`. |
| 2026-09-20 | Multi-point calibration simplified to average ratio | Regression + intercept added complexity and was the path to the NVS race condition. Simple average of `rawCounts/weightKg` is more robust for industrial load cells and easier to verify. | Frontend computes `avg(raw/weight)`, backend applies `countsPerKg` only, `calIntercept` forced to `0`. Updated UI metrics and removed `intercept` parameter from `/api/calibrate/multi`. |
| 2026-09-20 | NVS access serialised with a recursive mutex instead of "one writer per core" | The earlier "single writer on one core" rule removed the portal-side save but did not fix the underlying problem: `SettingsStore` still shared one `Preferences` handle across cores (totals every 30 s on the sensor core vs. WiFi/factory writes on the network core). A recursive mutex in `SettingsStore` makes every access atomic and lets both cores persist what they own. | `SettingsStore::begin()` creates the mutex in `setup()`; all public methods lock/unlock it. New `saveCalibrationValues()` writes only the three calibration keys so a stale cached offset can never overwrite a fresh tare. |
| 2026-09-20 | Radio work must never run inside an HTTP handler | `POST /api/wifi` previously called `WiFi.disconnect()`/`WiFi.begin()` before answering, which stalled the response and made "Apply Configuration" look dead. Mutating handlers now answer first and hand long-running work (WiFi reconfiguration, restart) to the network task loop via `WifiManager::requestSettings()` and `WebPortal::scheduleReboot()`. | `WIFI_APPLY_DELAY_MS` = 750 ms before the uplink is reconfigured; `CALIBRATION_REBOOT_DELAY_MS` = 1200 ms before `ESP.restart()`, extended until no scale command is pending. |
| 2026-09-20 | Calibration apply persists first, then restarts the ESP32 | Guarantees the new coefficients are in NVS before the CPU resets and that the sensor task is reloaded with a clean, deterministic state (same path as a power cycle). | Both `/api/calibrate` and `/api/calibrate/multi` save to NVS, queue `CMD_CALIBRATE_MLR`, then restart; the UI shows a reboot overlay, polls `/api/status` and reloads itself. `FW_VERSION` bumped to 1.2. |
| 2026-09-20 | Fix calibration points lost after reboot | ✅ | Root cause: the frontend computed the average locally and called `/api/calibrate/multi`, which only saves the slope/intercept to NVS. The individual calibration points were never sent to the backend, so after reboot `/api/calibration/points` returned zero and the UI showed "No calibration points captured yet". Fix: frontend now persists the captured points in `localStorage` and reloads them from there when the backend returns none after a reboot. Calibration points are saved on capture, delete, and clear. | `firmware/transmitter-multi-core/data/js/app.js`: added `saveCalibPointsToStorage()` and fallback to `localStorage` in `loadCalibrationPoints()`. No backend firmware changes required. Verified with `node --check` clean on `data/js/app.js`. |
